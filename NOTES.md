# Notes

## Decisions
- **PostgreSQL is the source of truth for correctness.** A `(campaign_id, member_id)` key and a partial unique `(campaign_id, branch_id, scheduled_at)` index keep sends unique. A composite FK ties every send's branch to its member's branch. A trigger enforces `planned → sent → final`, keeps the three final statuses terminal, and makes plan fields immutable. Application code repeats these rules, so the database acts as the backstop.
- **Planning.** Slots are built from local calendar dates (Mon–Sat, 09:00–19:58, every 2 min) and converted to UTC with IANA zones, so London's 25 Oct DST change moves the UTC offset, not the local times. The first plan call locks the campaign row, reads membership in one statement (a single snapshot), inserts all 5,000 rows and sets `planned_at` in the same transaction. Later or concurrent calls see `planned_at` and return the stored plan. A plan is immutable: changing membership needs `npm run reset` before replanning. The campaign dates are in the past, but they are still planned exactly as configured.
- **Webhooks.** The raw body is committed as bytes (`bytea`, exact even for non-UTF-8 input) in its own transaction **before** parsing. A second transaction claims the `eventId` in `provider_events` (`ON CONFLICT DO NOTHING`), then runs a conditional `UPDATE` that rechecks the current status under the row lock. The first committed final status wins regardless of `occurredAt`. `occurredAt` is stored but never reopens a final status. A reused `eventId` with a different body is stored as a receipt but not processed. Updates are published to SSE only after commit.
- **Response codes.** `200` covers applied, duplicate, ignored-stale and ignored-unknown-send events. Unknown sends are recorded and acknowledged so the provider stops retrying. `400` means malformed JSON or a schema violation (the receipt is kept). `503` means the receipt or processing failed transiently; the event transaction rolled back, so the provider's retry is safe.
- **Live UI.** The client opens SSE first and waits for `ready`, which the server sends after subscribing it. Then it loads the summary and five 1,000-row pages. Rows merge by `statusVersion`, so a slow page cannot overwrite a newer event, and an event for a row that hasn't loaded yet is held until it arrives. Branch counts move by deltas from the cached row's previous status. Every reconnect reloads the snapshot. Renders are flushed at most once per animation frame. The table is virtualized and rows are memoized, so 50+ updates/s only re-render changed visible rows.
- **Why not Redis/BullMQ or polling:** a queue adds infrastructure the planner must not use, and polling repeats work and adds lag. SSE from one process is enough here.

## Omitted
Auth and rate limiting on the webhook (a real provider would also sign it, e.g. with HMAC), a real SMS provider, the timer/worker that would actually send due messages, observability (metrics, tracing), receipt retention and partitioning, and UI search and pagination beyond client-side filters.

## First limits at 100 branches / 5 million members
- **Capacity.** Each branch has 1,980 slots per campaign week. With about 50k members per branch, roughly 96% of members would be `not_scheduled`, which is a product problem before it is a technical one.
- **Planning.** A single transaction with 5M rows through `unnest` arrays holds the campaign lock for a long time and uses a lot of memory. Plan each branch in its own chunk using `COPY` into a staging table, or stream from `INSERT … SELECT` with slots generated in SQL, then mark the campaign planned when every branch is done.
- **Reads.** `count(*) GROUP BY` summaries over millions of rows become slow, so keep per-branch counter rows updated in the webhook transaction, or roll them up. The dashboard can't load every send either; it would need server-side filtered pages and aggregate-only live updates.
- **Fan-out and storage.** The in-process SSE hub stops working once the API runs on several instances; use Postgres `LISTEN/NOTIFY` or Redis pub/sub. `webhook_receipts` grows by about 10–30M rows per campaign, so partition it by `received_at` and expire old partitions.

## Exactly-once sending in production
Write each due send to an outbox. Workers claim batches with `SELECT … FOR UPDATE SKIP LOCKED`, take a short lease (`claimed_until`, `attempts`), and call the provider with an idempotency key equal to the send id. When the provider accepts, record the provider message id and move the send to `sent`. An expired lease makes the send claimable again. This design prevents two workers from sending concurrently. It cannot guarantee exactly-once delivery across a crash between the provider accepting a message and the commit. That guarantee needs **provider-side idempotency** on the key, or a status lookup by that key before any retry. Without one of those, the system can promise at most "at-least-once, never concurrent".
